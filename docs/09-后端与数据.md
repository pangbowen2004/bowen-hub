# 09 后端与数据

## 1. 服务平面：`services/api`

一个 Cloudflare Worker，基于 Hono。它是**唯一**能读写数据库和对象存储的代码。

```text
services/api/
├── wrangler.jsonc            # 绑定：D1（DB）、R2（FILES）、机密（见 12）
├── src/
│   ├── index.ts              # Worker 入口：挂载 Hono 应用、Better Auth、MCP
│   ├── app.ts                # 中间件：请求 ID、日志、错误（problem+json）、鉴权分流
│   ├── routes.gen.ts         # 由契约生成的路由骨架（全部接口预先接好，未实现的返回 501）
│   ├── db/schema/            # 全部 Drizzle 表定义（第 3 节），集中一处
│   ├── modules/
│   │   ├── news/             # routes.ts · service.ts · repo.ts · mcp.ts（本模块的 MCP 工具）
│   │   ├── watchlist/
│   │   ├── markets/
│   │   ├── papers/
│   │   ├── platform/         # documents、runs、aiCalls、evals、export
│   │   └── mcp/              # MCP 服务：server.ts（传输与鉴权）、registry.ts（汇总各模块的 mcp.ts）
│   └── lib/                  # db、r2、auth、github（repository_dispatch）
├── migrations/               # D1 迁移（drizzle-kit 生成）
└── test/                     # Vitest（Workers 测试环境）
```

分层：`routes`（HTTP 适配，用生成的 Zod 校验入参出参）→ `service`（用例）→ `repo`（Drizzle/D1）或 `lib`（R2、AI、GitHub）。模块之间只通过 `service` 的导出函数调用，不直接读别的模块的表。

**CPU 预算**：免费版每次请求 10 ms CPU。规则：
- 大文档（如 `MarketDay` 约 130 KB、`Paper` 约 100 KB）以 JSON 文本整块存取，读出后直接返回，不在 Worker 里解析再重组。
- **大文档连同它的摘要一起写入**：计算任务写 `PUT /v1/internal/markets/days/{date}` 时，请求体是 `{ day, summary }`；写论文是 `{ paper, summary }`。摘要（`MarketDaySummary`、`PaperSummary`）是契约里的小模型，由计算任务算好，API 存进单独的列，列表页只读摘要。
- 写入时的完整校验在计算平面做（发送前用生成的 Pydantic 模型校验）；API 只解析 JSON、检查 `schemaVersion` 和主键字段是否与路径一致。
- 控制台改论文的某个字段（公开状态、研究空间等）时，用 SQLite 的 `json_set` 在数据库里原地修改，Worker 不解析整篇文档。
- 列表接口分页，单页不超过 100 条；统计用 SQL 聚合。
- 按需 AI 用流式返回；等待模型是 IO，不占 CPU。逐块解析流如果超出 CPU 限制，就直接转发网关的流（`10` 第 5 节）。
- 任何需要循环计算的逻辑都不该出现在 API 里，应该放到计算平面提前算好。

## 2. 鉴权

| 对象 | 方式 |
|---|---|
| Kevin（控制台） | Better Auth + 通行密钥（passkey）。第一次注册通行密钥需要一次性口令 `HUB_BOOTSTRAP_TOKEN`（Kevin 自己用 `wrangler secret put` 设置，`12` 第 4 节）；注册完成后该口令作废。会话用 HttpOnly、Secure、SameSite=Lax 的 Cookie，只在控制台域名下 |
| AI 客户端（MCP） | Better Auth 的 MCP 插件充当 OAuth 2.1 授权服务器（客户端注册方式按插件实现时支持的来）；登录页就是通行密钥登录。只开放第 6 节列出的工具 |
| 计算任务 | 服务令牌 `HUB_SERVICE_TOKEN`：可以写 `/v1/internal/*`，也可以读 `/v1/*` 的全部 GET 接口 |
| 访客 | 只能访问 `/v1/public/*`（只读、只含公开数据） |

只有一个用户，不做注册、找回密码、多租户。

鉴权上线前（T40 合并前）的占位中间件：本地 `wrangler dev` 放行私有接口，线上一律返回 401。私人数据（笔记、私有论文）在鉴权上线后才导入（`tasks/graph.yaml` 里 T50 依赖 T40）。

## 3. 数据模型（D1）

建表在预接线任务 T02 里**一次建全**（见 `11` 第 5 节），后续任务尽量不再加迁移。表按模块归属：

| 模块 | 表 | 要点 |
|---|---|---|
| 新闻室 | `news_sources` | 各来源的健康状态：`id`、最近一次检查时间、状态、错误信息（来源清单本身以 `config/news_sources.yaml` 为准，这张表只记运行结果） |
| | `articles` | 归一后的条目；`dedupe_key` 唯一（规范化链接；Alpaca 新闻用它的新闻 id）；`tickers`、`topics` 为 JSON；`published_at` 索引 |
| | `articles_fts` | FTS5 虚拟表（标题 + 摘要），供搜索 |
| | `filings`、`insider_trades`、`calendar_events` | SEC 公告、Form 4、日程。自然键：`filings` 用 `accession`；`insider_trades` 用 `accession` + 交易行序号；`calendar_events` 用 类型 + 日期 +（FRED release id 或股票代码） |
| | `earnings_cards` | 财报卡片（`symbol` + 来源主键：8-K 的 `accession` 或新闻 url；`period` 只用来显示；发布时间、`payload`） |
| | `editions` | `id`（如 `morning-2026-09-30`）、`kind`、`date`、`payload`（Edition JSON）、`email_sent_at` |
| | `edition_feedback` | 每期打分、单条“没用 / 有错”标记 |
| 自选股 | `watch_items` | 代码、名称、类型、分组、标的、对照板块 ETF、别名、启用 |
| A 股观测台 | `market_days` | `date` 主键、`complete`、`summary`（MarketDaySummary JSON）、`payload`（MarketDay JSON） |
| | `market_hypotheses` | `id` 主键、`created_on`、`due_on`、`result`、`mode`、`payload` |
| | `market_weeklies` | `date` 主键、`payload`（WeeklyReport JSON，含 Markdown 版） |
| | `market_events` | 事件日历（`03` 第 6.3 节） |
| | `index_history` | 6 个指数的日线（K 线用）：`code` + `date` 主键、OHLC、成交额 |
| 论文库 | `papers` | `id`、`visibility`、`review`、`reading_depth`、`year`、`spaces`（JSON 数组，筛选用 `json_each`）、`updated_at`、`summary`（PaperSummary JSON）、`doc`（Paper JSON） |
| | `papers_fts` | FTS5（标题、中文标题、一句话、概念） |
| | `paper_private` | 掌握状态、笔记、解释卡、老阅读卡（JSON） |
| | `paper_reviews` | 审核记录（每次审核一条） |
| | `paper_uploads` | 上传与入库状态：`queued` → `extracting` → `authoring` → `checking` → `reviewing` → `ready` / `failed` |
| 平台 | `documents` | 通用的“单份文档”：`key` 主键、`payload`、`updated_at`。存派生数据和参考资料，如 `papers.catalog.public`、`papers.graph.all`、`markets.reference` |
| | `runs` | 任务运行台账：任务名、日期、状态、开始/结束、统计、错误 |
| | `ai_calls` | 能力、版本、模型、输入/输出 token、费用、耗时、是否成功、所属运行 |
| | `eval_results` | 能力、模型、评测集版本、各项得分、是否通过、时间 |
| 鉴权 | Better Auth 自带表 | 用户、会话、通行密钥、OAuth 客户端与令牌（按 Better Auth 的通行密钥 + MCP 插件生成，定义放在 `db/schema/auth.*`） |

**保留策略**：`articles` 在 D1 留 365 天。每晚导出（第 5 节）成功后，导出任务调用 `POST /v1/internal/news/articles/prune?before=<365 天前>` 删除更早的条目——它们仍保存在数据仓库 `bowen-hub-data` 的 git 历史里。其余表长期保留。

## 4. 对象存储（R2）

```text
papers/<id>/source.pdf
papers/<id>/pages.jsonl         # 带行号的页文本：每行 {"page": n, "lines": [...]}，行号 = 下标 + 1（格式见 04 第 5.1 节；入库时生成；证据校验用）
papers/<id>/pages.txt           # 整篇原文，每页以 "=== p.N ===" 开头（入库时生成；问答直接放进上下文）
papers/<id>/pages/<n>.png       # 原文页图（入库时用 PyMuPDF 生成）
editions/<id>.html              # 每期邮件的 HTML 存档
uploads/<uploadId>.pdf          # 控制台上传的原始文件
```

控制台下载 / 查看文件时，由 API 流式读取 R2 返回，不暴露存储桶。

## 5. 备份与历史

- D1 自带 Time Travel（免费版 7 天），用于误操作恢复。
- 计算任务 `hub export` 每晚通过 `GET /v1/internal/export/{table}` 分页读出除鉴权表以外的所有表，按表写成 JSON 文件，提交到私有仓库 `bowen-hub-data`。git 历史就是完整的数据历史，Agent 也能直接看数据的变化。R2 里的文件不导出（PDF 在老目录里有原件，页文本和页图可以重新生成）。
- 导出结束时顺带检查月度 AI 预算（`10` 第 4 节）：本月 AI 费用超过 `config/llm.yaml` 的 `monthlyBudgetUsd` 就发一封提醒（失败通知邮件），并在 `runs` 表记一条 `budget-alert`；同一个月只发一次。
- 不做哈希账本、签名等额外防护。

## 7. 计算平面：`py/`

```text
py/
├── pyproject.toml                 # uv 工作区根
├── packages/
│   ├── hub-contracts/             # 生成的 Pydantic 模型（只读）
│   ├── hub-core/                  # 配置、HTTP（重试/超时）、API 客户端（生成模型 + 服务令牌）、邮件、日志、
│   │                              # 数据源协议与交易日历协议（纽交所日历的实现也在这里）
│   ├── hub-ai/                    # AI 运行时：读能力清单与提示词、按档位选模型、结构化输出、校验注册、评测
│   ├── hub-providers/             # 每个外部源一个子包：tushare/（含 A 股交易日历）rss/ alpaca/ tiingo/ sec/ fred/ finnhub/ treasury/ cboe/
│   ├── hub-market/                # A 股：compute/ summary/ hypotheses/ evolution/ weekly/（纯逻辑）；eod/（含 backfill）compare/ migrate/（编排）
│   ├── hub-newsroom/              # pipeline/ ai/（纯逻辑）；editions/ render/ migrate/（编排）
│   └── hub-papers/                # check/ derive/ excerpt/ ids/ ai/（纯逻辑）；pdf/ ingest/ revise/ localtask/ migrate/（编排）
└── apps/hub-cli/                  # typer 入口：只负责建好命令组、加载各包注册的子命令
```

- **子命令插件化**：`hub-cli` 建好 7 个命令组（news、market、papers、migrate、evals、providers、export）。每个实现目录有自己的 `commands.py`，里面一个 `register(groups)` 函数把命令加进对应的组；各包在 `pyproject.toml` 的 `hub.commands` entry point 里登记这些 `commands.py`。T03 预接线时把全部 entry point 和 `commands.py` 占位都建好（占位命令退出码 2 并提示任务号），之后每个任务只改自己目录里的 `commands.py`，没人需要改同一个文件。
- **幂等**：每个任务先查 API（比如“这一天是否已完成”），再决定做不做；写入用 `PUT`。
- **运行台账**：任务开始和结束各 `PUT /v1/internal/runs/{runId}` 一次（`runId` 由任务生成，如 `news-morning-2026-09-30-<GitHub 运行号>`）；AI 调用经 `POST /v1/internal/ai-calls/batch` 记进 `ai_calls`。
- **外部请求**：统一经 `hub-core` 的 HTTP 客户端（超时、有限重试、指数退避、记录来源健康）。
- **测试**：外部 HTTP 一律用录制的响应（`fixtures/http/`，pytest 的 cassette 方式），测试不联网；另有 `hub providers check`（数据源）和 `hub providers check-models`（模型）做真实连通性检查。

主要命令（完整说明在各产品文档）：

```bash
# 新闻室（02）
hub news morning|premarket|weekly [--date] [--no-email] [--no-ai] [--force]
hub news sources --check
# A 股观测台（03）
hub market eod [--date] [--force] [--deadline 22:00] [--dry-run <输出文件>]
hub market backfill --start 2026-07-01 --end <date>
hub market compare <date> [--input <文件>]      # 与 fixtures 里的老输出对照（07 第 4 节）；不给 --input 就用 fixtures/tushare 离线计算
# 论文库（04）
hub papers ingest <uploadId> | --file <PDF> | --arxiv <链接>   # 入库流水线（工作流用 uploadId；本机可直接给文件或链接）
hub papers revise <id> [--instructions <文字>]  # 按意见重写草稿
hub papers check <id|草稿文件>                  # 只做确定性校验
hub papers task <id> | --file <PDF>             # 让本机的 Agent 代写：生成 TASK.md（04 第 5.3 节）
hub papers submit <id> | --file <PDF> <草稿文件>   # 用 Agent 写好的草稿走完校验、审核、写入
hub papers derive                               # 生成目录、图谱、搜索索引（公开 / 全部两份）
# 迁移（06）
hub migrate papers|news-legacy|watchlist|market-ledger|market-events [--dry-run] [--verify]
# 平台
hub evals run [--capability <id 或通配>] [--changed] [--offline]
hub evals compare --candidate <模型> [--capability <id 或通配>]
hub evals harvest                               # 把控制台里的“有错 / 没用”反馈转成评测用例草稿
hub providers check                             # 外部数据源的真实连通性检查
hub providers check-models                      # 经 AI Gateway 列出模型、核对三个档位（由 hub-ai 的 commands.py 注册）；两条合起来就是完整的真实连通性检查
hub export
```

`--dry-run <输出文件>`：只计算，把结果写到本地文件，不写 API。用于对照和调试。

## 8. 调度（GitHub Actions）

cron 用 UTC；北京时间与新加坡时间都是 UTC+8，美东时间由任务内部用时区库判断。

| 工作流 | cron（UTC） | 本地时间 | 说明 |
|---|---|---|---|
| `news-morning.yml` | `10 23 * * *` 和 `40 23 * * *` | 新加坡 07:10 / 07:40 | 早报；第二个触发点是后备：第一次已发送就立即退出 |
| `news-premarket.yml` | `40 12 * * 1-5` 和 `40 13 * * 1-5` | 新加坡 20:40 / 21:40 | 任务内判断：只在美东 08:35–09:15 之间、且当天是纽交所交易日时运行，否则立即退出（两个触发点分别对应夏令时和冬令时；时间窗口留出 GitHub 定时触发的延迟） |
| `news-weekly.yml` | `10 1 * * 6` | 周六 09:10 | 周报 |
| `market-eod.yml` | `5 9-14 * * 1-5` | 北京 17:05–22:05 每小时 | A 股收盘；完成后发出 `markets-updated`，触发 `deploy-markets` |
| `papers-ingest.yml` | `repository_dispatch`（`papers-ingest`、`papers-revise`） | — | 控制台上传、MCP 提交或“按意见重写”后由 API 触发 |
| `evals-weekly.yml` | `0 19 * * 6` | 周日 03:00 | 全量评测（`10` 第 7.3 节） |
| `data-export.yml` | `30 19 * * *` | 每天 03:30 | 导出到 `bowen-hub-data` |
| `deploy-*.yml`、`ci.yml` | push / PR / dispatch | — | 见 `12` 第 3 节 |

每个工作流都设 `concurrency`，同一任务不重叠。GitHub 的定时触发可能延迟几分钟到几十分钟，这是多设触发点和“任务内判断时间”的原因。

所有定时工作流都同时支持手动触发（`workflow_dispatch`），输入项：`date`（默认今天）、`force`（重跑已完成的）、`ignore_window`（盘前简报跳过时间窗判断），用于验收、补跑和排错。

## 9. 失败处理与可观测性

- 任务失败：非零退出（Actions 标红）+ 失败通知邮件（标题 `⚠️ [任务名] 失败｜日期`，正文含错误摘要和 Actions 运行链接）+ `runs` 表记为 failed。
- 部分失败：能出的先出，缺的写进产出文档的 `missing`，页面或邮件如实显示。
- 可观测：Workers 自带日志；AI Gateway 的请求日志与费用统计；控制台“运维”页汇总 `runs`、`ai_calls`、来源健康、评测结果。
