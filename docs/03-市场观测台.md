# 03 市场观测台（Market Observatory）

## 1. 目标

每个 A 股交易日收盘后，自动生成一份**可复算**的市场复盘：今天市场处在什么状态，哪里强、哪里弱，涨停生态和量能怎样，明天要验证什么，昨天提出的问题验证得怎么样。

- 每个数字都能在“方法与口径”页找到定义、公式和数据源。
- 只描述状态。不给买卖建议、仓位、目标价、概率或胜率。
- 公开网址：https://bowen-market-observatory.pages.dev/ （保持不变）

本文件第 4、5、6 节的公式和阈值来自老系统的实际代码，已经在老数据上跑过。**照这些实现，不要自己改口径**；标了“修正”的地方是有意改动的。

## 2. 运行

`hub market eod [--date YYYY-MM-DD] [--force] [--deadline 22:00] [--dry-run <输出文件>]`（由 `market-eod.yml` 在北京时间 17:05–22:05 每小时触发，见 `09` 第 8 节）

1. 用 `trade_cal` 判断 `date`（默认今天，北京时间）是不是交易日；不是就以退出码 0 结束。
2. 查 API：这一天已经存在且 `complete = true`，直接结束（`--force` 除外）。
3. 拉取数据（第 3 节）。**核心表**没就绪：北京时间早于 `--deadline` 就打印“数据未就绪”并以 0 退出，等下一个触发点；已过 deadline 就以非零退出（触发失败通知）。
4. 计算（第 4 节）。
5. 结算到期假设、生成新假设（第 5 节）；计算近五日演化（第 6.1 节，需要的前几天数据从 API 的交易日摘要读取）。
6. 写入 API（顺序固定，全部是覆盖式写入，重跑结果相同）：
   1. `POST /v1/internal/markets/hypotheses/batch`（本次结算的 + 新生成的）；
   2. `PUT /v1/internal/markets/indices/{code}/bars`（6 个指数的日线）；
   3. `PUT /v1/internal/markets/days/{date}`，请求体 `{ day, summary }`：`day` 是完整的 `MarketDay`（第 7 节），`summary` 是 `MarketDaySummary`；
   4. 如果 `date` 是本周最后一个交易日：`PUT /v1/internal/markets/weeklies/{date}`（第 6.2 节）；
   5. `PUT /v1/internal/documents/markets.reference`（指标说明、方向、ETF 分组、主题、指数、数据源（含做不到的事和免责声明）；内容来自 `config/`，其中数据源部分来自 `config/market_sources.yaml`；每次都写，保证网站和配置一致）。
7. 发出 `repository_dispatch: markets-updated`，由 `deploy-markets.yml` 从 API 构建并发布网站（`12` 第 3 节）。

`--dry-run <输出文件>`：只计算，把 `{ day, summary, hypotheses, weekly }` 写进本地文件，不写 API、不触发部署。

`hub market backfill --start <date> --end <date>`：按交易日顺序逐天执行 `eod`，跳过已完成的日期，最后只触发一次部署。用来补历史（从 2026-07-01 起，见 `06`）。说明：`ths_member` 只能拿到**当前**成分，补跑的历史日期里，方向的宽度类指标用的是今天的成分，产出里用 `membershipAsOf` 写明。

**非核心数据缺失时照常发布**：哪个接口失败，受它影响的块或字段在产出里为 `null`，同时写进 `dataStatus.missing`（对照表见第 7 节），`dataStatus.complete = false`，页面显示“今日该部分数据未就绪”。当天后面的触发点会自动重跑补齐；假设按 ID 覆盖写入，重跑不会重复生成；同一 ID 已经结算的假设保留原结果，只有仍是 `PENDING` 的才覆盖。

## 3. 数据源（TuShare）

| 接口 | 用途 | 取数范围 | 用到的字段（单位） | 核心 |
|---|---|---|---|---|
| `trade_cal`（exchange=SSE） | 交易日历、上一交易日 | 按需 | `cal_date` `is_open` `pretrade_date` | ✅ |
| `daily`（按 trade_date） | 全 A 日线 | 回看 65 个交易日 | `open` `high` `low` `close` `pre_close` `pct_chg`（%）`amount`（千元） | ✅ 当日 ≥ 5000 行 |
| `daily_basic`（按 trade_date） | 换手、估值、市值 | 当日 | `turnover_rate`（%）`volume_ratio` `pe_ttm` `pb` `total_mv`（万元）`circ_mv`（万元） | ✅ ≥ 5000 行 |
| `stk_limit`（按 trade_date） | 涨跌停价 | 回看 30 个交易日 | `up_limit` `down_limit` | ✅ ≥ 5000 行 |

| `index_member_all` | 申万 2021 一级行业**点时**成员 | 每周刷新全量（包括 `is_new=N` 的历史成员） | `l1_code` `l1_name` `ts_code` `in_date` `out_date` | ✅ |
| `index_daily` | 6 个指数日线（`config/market_indices.yaml`） | 回看 250 个交易日 | OHLC、`pct_chg`、`amount` | ✅ |
| `limit_list_d`（按 trade_date） | 涨跌停明细（U 涨停 / D 跌停 / Z 触板未封） | 当日 | `limit` `first_time` `last_time` `open_times` `up_stat` `limit_times` `fd_amount` | 可选 |
| `moneyflow_dc`（按 trade_date） | 个股资金流分类代理 | 当日 | `net_amount` `buy_elg_amount` `buy_lg_amount`（万元） | 可选 |
| `moneyflow_mkt_dc`（按 trade_date） | 全市场资金流分类代理 | 当日 | `net_amount` `net_amount_rate` `buy_elg_amount` `buy_lg_amount` `buy_md_amount` `buy_sm_amount` | 可选 |
| `fund_basic`（market=E, status=L） | ETF 名单 | 每周刷新 | `name` `fund_type` `list_date` | 可选 |
| `fund_daily`（按 trade_date） | ETF 日线 | 回看 21 个交易日 | `close` `pct_chg`（%）`amount`（千元） | 可选 |
| `fund_share`（按 trade_date） | ETF 份额**变动记录** | 当日 + 上一交易日 | `fd_share`（万份） | 可选 |
| `ths_member`（按 ts_code） | 16 个方向的当前成分 | 每个交易日 | `con_code` `con_name` | 可选 |
| `ths_daily`（按 ts_code） | 16 个方向的官方板块日线 | 回看 30 个交易日 | `close` `pct_change`（%）`turnover_rate` | 可选 |

- 账号是 TuShare 8000 积分档：需要更高积分或需要单独开通权限的接口不用，对应的内容不做（T20 真实运行时逐个核对接口权限，超出的列进进度记录）。
- 单位换算：`daily.amount`、`fund_daily.amount` × 1000 = 元；`daily_basic.total_mv` × 10000 = 元；`moneyflow_dc` 金额 × 10000 = 元。`moneyflow_mkt_dc` 的金额单位以接口文档为准（老系统当作“元”直接用，8 月 28 日全市场净额约 −343.7 亿元），实现时写一个测试核对量级。
- 缓存：`.cache/tushare/<接口>/<trade_date 或 key>.parquet`。历史日期优先读缓存；当天的数据每次都重新拉。在 GitHub Actions 里用 `actions/cache` 保存和恢复这个目录（`12` 第 3 节）；缓存丢了只是多拉一次数据，不影响结果。
- 并发不超过 4；遇到限流或网络错误重试 3 次，指数退避。

## 4. 计算口径

所有计算都是纯函数（输入 DataFrame，输出 pydantic 模型），每个函数都有单元测试。

### 4.1 个股面板（当日）

- **有效样本**：当日在 `daily` 里有记录且 `pct_chg` 非空的股票。
- `return1d = pct_chg / 100`；`amountCny = amount × 1000`。
- `return5d = close / close[t−5] − 1`，`return20d = close / close[t−20] − 1`。`t−5` 指**这只股票自己的**第 5 个前序交易日（停牌日不算）；历史不够就为空。
- `ma20` = 这只股票最近 20 个交易日收盘价均值（含当日）；不足 20 天就用已有天数的均值（与老系统一致）。`aboveMa20 = close > ma20`。
- `newHigh20 = close ≥ 最近 20 个交易日最高收盘价`（含当日）；`newLow20 = close ≤ 最近 20 个交易日最低收盘价`。注意用的是**收盘价**。
- `limitUp = |close − up_limit| < 0.001`；`touchLimitUp = high ≥ up_limit − 0.001`；`limitDown = |close − down_limit| < 0.001`。
- `boardHeight`：按这只股票自己的交易日序列（停牌日跳过），从当日往前数连续“收盘价 = 涨停价”的天数，最多回看 30 个交易日。**修正**：老系统只回看 10 天，10 板以上会被截断。
- **昨日涨停股**：在上一交易日（按交易日历）收盘涨停的股票；`prevBoardHeight` 是它截至上一交易日的连板高度，不是昨日涨停股则为 0。**修正**：老系统按每只股票自己的交易日序列取“上一日”，当天停牌的股票会被错算进昨日涨停组。
- **上市板**（按代码）：`300`/`301` 开头 → 创业板；`688`/`689` → 科创板；`4`、`8`、`92` 开头 → 北交所；其余 → 主板。
- **行业**：申万 2021 一级。点时成员：`in_date ≤ date` 且（`out_date` 为空或 `out_date > date`）；同一只股票有多条时取 `in_date` 最新的一条。
- **市值**：`total_mv × 10000`（元）。

### 4.2 全市场 `market`

| 字段 | 定义 |
|---|---|
| `sampleCount` | 有效样本数 |
| `advanceCount` / `declineCount` / `flatCount` | `return1d` > 0 / < 0 / = 0 的家数 |
| `advanceShare` | `advanceCount / sampleCount` |
| `medianReturn1d` | `return1d` 中位数 |
| `aboveMa20Share` | `aboveMa20` 家数 / 有 `ma20` 的家数 |
| `newHigh20Count` / `newLow20Count` | 20 日新高 / 新低家数 |
| `turnoverCny` | 有效样本 `amountCny` 之和 |
| `turnoverPrevCny` | 上一交易日同口径成交额 |
| `turnoverChange` | `turnoverCny / turnoverPrevCny − 1` |
| `turnoverMedian20Cny` | 最近 20 个交易日（含当日）全市场成交额的中位数 |
| `medianTurnoverRate` | 换手率中位数（%） |
| `medianPeTtm` / `medianPb` | 只统计 > 0 的值的中位数 |
| `totalMarketCapCny` | 总市值之和 |

### 4.3 指数

6 个指数见 `config/market_indices.yaml`：上证指数、科创50、深证成指、创业板指、中证1000、国证2000。每天输出收盘、涨跌幅、成交额；指数日线另外写进 API 的 `index_history` 表（`PUT /v1/internal/markets/indices/{code}/bars`），网站 K 线读最近 250 个交易日。

### 4.4 收盘温度 `temperature`（0–100，版本 `transparent-close-v1`）

| 分项 | 满分 | 公式 |
|---|---|---|
| 广度 `breadth` | 35 | `advanceShare × 35` |
| 趋势 `trend` | 20 | `aboveMa20Share × 20` |
| 涨跌停生态 `limitEcology` | 15 | `涨停家数 / max(1, 涨停家数 + 跌停家数) × 15` |
| 量能 `liquidity` | 15 | `clip((turnoverChange + 0.10) / 0.20, 0, 1) × 15` |
| 指数 `positiveIndices` | 15 | `当日上涨的指数个数 / 6 × 15` |

`value = round(五项之和, 1)`，各分项保留 2 位小数。
对照：2026-08-28 = **51.9**（19.01 / 11.72 / 14.48 / 6.69 / 0.00）。
页面说明：“透明的收盘状态合成，不是概率、仓位或交易信号。”

### 4.5 情绪九维 `sentiment`（0–100，版本 `transparent-ecology-v2`）

| key | 名称 | 满分 | 输入 | 公式 |
|---|---|---|---|---|
| `limitHeight` | 连板高度 | 15 | 最高连板 | `min(最高连板 / 7, 1) × 15` |
| `limitUpCount` | 涨停家数 | 12 | 涨停家数 | `min(涨停家数 / 100, 1) × 12` |
| `sealRate` | 封板成功率 | 12 | 封板率 = 涨停家数 / 触板家数 | `min(封板率 / 0.85, 1) × 12` |
| `advancementRate` | 前日晋级率 | 12 | 昨日涨停股中今日仍涨停的比例 | `min(晋级率 / 0.30, 1) × 12` |
| `previousLimitPremium` | 前日涨停溢价 | 12 | 昨日涨停股今日 `return1d` 均值 | `clip((溢价 + 0.02) / 0.05, 0, 1) × 12` |
| `lossEffect` | 亏钱效应 | 9 | 跌停家数、跌幅 ≥ 7% 家数 | `(1 − min(跌停 / 10, 1)) × 4.5 + (1 − min(跌逾7% / 30, 1)) × 4.5` |
| `breadth` | 上涨广度 | 9 | `advanceShare` | `min(advanceShare / 0.60, 1) × 9` |
| `upDownBalance` | 涨跌停对比 | 9 | 涨停、跌停家数 | `min(涨停 / 80, 1) × 4.5 + (1 − min(跌停 / 8, 1)) × 4.5` |
| `turnover` | 市场量能 | 10 | `turnoverCny / turnoverMedian20Cny` | `clip((倍数 − 0.70) / 0.50, 0, 1) × 10` |

`value = round(九项之和, 1)`；每项输出 `key` `label` `weight` `input` `unit` `score` `formula`，页面可以逐项展开。
对照：2026-08-28 = **81.1**。

### 4.6 市场风格 `style`（版本 `transparent-style-v1`）

对每只有效样本按顺序判断，先命中先归类：

| 分组 | 条件 |
|---|---|
| 高位加速 | `return1d ≥ 3%` 且 `return5d ≥ 5%` 且 `aboveMa20` |
| 趋势延续 | `return1d > 0` 且 `return5d ≥ 3%` 且 `aboveMa20` |
| 低位修复 | `return1d > 0` 且不在 MA20 上方 |
| 中间状态 | 其余 |

`return5d` 为空按 0 处理。每组输出家数、占比、`return1d` 均值和中位数；`trendStrongShare = (高位加速 + 趋势延续) / 样本数`。

### 4.7 涨停生态 `limitEcology`

| 字段 | 定义 |
|---|---|
| `limitUpCount` / `limitDownCount` | 收盘涨停 / 跌停家数 |
| `touchedCount` / `failedCount` | 触板家数（含封住的）/ 触板但未封住的家数 |
| `sealRate` | `limitUpCount / touchedCount`（触板为 0 时为空） |
| `maxBoardHeight` | 涨停股里最高的 `boardHeight` |
| `firstBoardCount` / `multiBoardCount` | `boardHeight = 1` / `≥ 2` 的涨停家数 |
| `previousLimitUpCount` | 昨日涨停股家数 |
| `advancementCount` / `advancementRate` | 昨日涨停股里今天仍涨停的家数 / 其占昨日涨停股的比例 |
| `previousLimitPremium` | 昨日涨停股今日 `return1d` 均值 |
| `largeLoss7Count` | `return1d ≤ −7%` 的家数 |
| `providerDetail` | `limit_list_d` 里 U / D / Z 的行数，仅作交叉核对 |

列表：
- `heightDistribution`：按高度从高到低，每档家数和最多 8 个名称。
- `industryClusters`：涨停股按行业聚类，按家数降序（同数按名称），每类输出家数、最高板、最多 6 个名称。
- `progression`：涨停股按（`boardHeight`，成交额）降序取前 20。状态：`prevBoardHeight > 0` 且 `boardHeight = prevBoardHeight + 1` → “连续晋级”；`boardHeight = 1` → “首板建立”；其余 → “重新封板”。
- `failedPromotions`：昨日涨停、今天没封住的股票，按 `prevBoardHeight` 降序、同高度按 `return1d` 升序，取前 16，状态“晋级未完成”。
- `leaders`：同 `progression` 的排序取前 20。`limitDownSamples`：跌停股按成交额降序前 12。`largeLossSamples`：`return1d` 最低的 12 只。
- 列表里的个股字段：代码、名称、行业、`return1d`、`boardHeight`、成交额、上市板；有 `limit_list_d` 明细时附上首次/最后封板时间、开板次数、`up_stat`、封单金额。

### 4.8 资金流代理 `moneyflow`（可选）

来自 `moneyflow_mkt_dc`：全市场净额、净额占比、超大单/大单/中单/小单净额；另记 `moneyflow_dc` 覆盖的个股数。页面固定说明：“供应商订单分类代理，不等于机构、游资或真实主体资金。”

### 4.9 申万一级行业 `industries`

- 只统计当日样本 ≥ 10 的行业。等权聚合：`return1d`（均值）、`medianReturn1d`、`return5d`、`return20d`（均值，忽略空值）、`advanceShare`、`aboveMa20Share`、`amountCny`、`amountShare`（占全市场成交）、涨停家数、跌停家数、`medianPeTtm` / `medianPb`（只统计 > 0）。
- **阶段 `lifecycle`**（按顺序判断，先命中先定）：

| 阶段 | 条件 |
|---|---|
| 趋势扩散 | `return5d ≥ 3%` 且 `advanceShare ≥ 55%` 且 `aboveMa20Share ≥ 55%` |
| 高位分歧 | `return5d ≥ 2%` 且 `return1d < 0` 且 `aboveMa20Share ≥ 55%` |
| 修复延续 | `return5d > 0` 且 `advanceShare ≥ 50%` |
| 退潮观察 | `return5d ≤ −3%` 且 `advanceShare ≤ 40%` |
| 低位修复 | `return1d > 0` 且（`return5d` 为空或 ≤ 0） |
| 方向待明 | 其余 |

- 按 `return1d` 降序排列；页面另给前 10、后 10。
- 页面说明：“申万一级点时成员等权聚合，不是行业指数收益。”

### 4.10 主题篮子 `themes`

8 个篮子见 `config/market_themes.yaml`（每个篮子由若干申万一级行业组成）。按成员行业的样本数加权平均 `return1d` `return5d` `return20d` `advanceShare` `aboveMa20Share`；`amountShare`、涨停、跌停家数直接相加。按 `return1d` 降序。

### 4.11 16 个方向 `directions`

清单见 `config/market_directions.yaml`（名称 → 同花顺板块代码）。对每个方向：
- 成员 = 当日 `ths_member` 的成分（当前快照，不是点时），与有效样本求交集。
- **收益用官方板块日线**：`return1d = ths_daily.pct_change / 100`；`return5d` / `return20d` = 官方收盘 ÷ 5 / 20 个交易日前的官方收盘 − 1（历史不够为空）。
- `componentCrossCheck`：成员等权的 1/5/20 日收益，以及 `delta1dVsOfficial = 成员等权 return1d − 官方 return1d`（只作交叉核对）。
- 成员统计：`medianReturn1d`、`advanceShare`、`aboveMa20Share`、`amountCny`、`amountShare`、涨停/跌停家数、`loss5Count`（`return1d ≤ −5%`）。
- `amount20dPercentile`：用当前成员算出最近 20 个交易日每天的成员成交额合计，今日值在这 20 个值中的分位（`≤ 今日值的个数 / 个数`）。
- `relativeVsAllA = 官方 return1d − 全 A 有效样本 return1d 的等权均值`。
- `moneyflowProxyCny`：成员 `moneyflow_dc` 净额之和（元）；`moneyflowCoverage` = 有资金流数据的成员 / 成员数。
- `leaders`：成员按（`return1d`，成交额）降序前 3；`laggards`：`return1d` 升序前 3。
- **状态 `state`**（按顺序判断）：

| 状态 | 条件 |
|---|---|
| 趋势扩散 | `return5d ≥ 5%` 且 `advanceShare ≥ 55%` |
| 高位分歧 | `return5d ≥ 3%` 且 `return1d < 0` |
| 低位修复 | `return1d > 0` 且 `return5d ≤ 0`（为空按 0） |
| 趋势转弱 | `return5d < −3%` |
| 方向待明 | 其余 |

- 按 `return1d` 降序。输出 `membershipAsOf`（成分快照日期）。
- 删除：老系统里的 `relativeVsCsi300`（沪深 300 不在指数清单里，这个字段一直为空）。

### 4.12 ETF 轮动 `etfGroups`（可选）

- 份额：`fund_share` 是**变动记录**，不是每天的全量快照。某只 ETF 当日和上一交易日都有记录时才算份额变化；`shareCoverage` = 有变化数据的只数 / 组内只数；统计增加、减少的只数。没有记录就是“不可用”，不能当作份额不变。
- `representative`：组内成交额最大的一只（代码、名称、`return1d`、成交额、份额变化）。
- 按 `amountWeightedReturn1d` 降序。

- 支撑：MA20、近 10 日最低价、近 20 日最低价。压力：近 10 日最高价、近 20 日最高价。

- **修正**：删掉老系统硬编码的外部价位（3975 / 4004–4007 / 4070）。

### 4.16 状态摘要 `summary`（规则生成，不用 LLM）

记 `a = advanceShare`，`m = aboveMa20Share`，`c = turnoverChange`。

**标题 `headline`**

| 条件 | 标题 |
|---|---|
| `a < 0.35` 且 `m ≥ 0.75` | 普跌回撤，趋势存量尚未完全破坏 |
| `a < 0.35` 且 `m < 0.75` | 普跌收缩，广度与量能同步转弱 |
| `a > 0.65` 且 `c > 0` | 广度与量能共振，持续性等待验证 |
| `a > 0.65` 且 `c ≤ 0` | 广度扩张，但仍需验证量能承接 |
| 其余 | 涨跌分化，市场仍在寻找一致方向 |

**标签 `tags`**：广度状态（`a < 0.35` 广度承压 / `a > 0.65` 广度扩张 / 其余 广度分化）、量能状态（`c < 0` 量能收缩，否则量能扩张）、`MA20上方{m:.0%}`、`{涨停家数}家封板`、`温度{temperature}`。

**摘要 `text`** = 第一句 + 结构句：
- 第一句：`全A收盘为{上涨}家上涨、{下跌}家下跌，上涨占比{a:.2%}；成交{成交额/1e12:.4f}万亿元，环比{c:+.2%}。`
- 结构句：
  - `a > 0.65`：`单日广度明显扩张，{m:.1%}样本位于MA20上方；{涨停}家封板、{跌停}家跌停，广度与涨停生态相互印证。这确认了当日扩张，但持续性仍需下一交易日验证。`
  - `a < 0.35`：`单日广度显著转弱，但{m:.1%}样本仍站在MA20上方，同时有{涨停}家封板、{跌停}家跌停，更接近结构分歧，而不是所有趋势同步失效。`
  - 其余：`涨跌覆盖处于分化区，{m:.1%}样本位于MA20上方；{涨停}家封板、{跌停}家跌停，尚不能仅凭单日截面确认统一方向。`

**支持 `support`**：`16方向中{最强方向}当日{其 return1d:+.2%}居前；{触板}家触板、封板率{封板率:.1%}，最高{最高板}板。`

**反证 `counterEvidence`**：`{最弱行业}当日等权{return1d:+.2%}，{最弱方向}方向{return1d:+.2%}；成交额环比{c:+.2%}，资金流分类代理{全市场净额，亿元，带正负号，1 位小数}。`（资金流缺失时省略最后一段。）

**三项风险 `risks`**
1. 广度：`a > 0.65` → 标题“普涨后的广度持续性尚未确认”，内容 `上涨占比{a:.2%}、中位数涨幅{中位涨幅:+.2%}；单日扩张不等同连续扩张。`；`a < 0.35` → “单日市场广度明显承压”，`下跌{下跌}家，上涨占比仅{a:.2%}；中位数涨幅{中位涨幅:+.2%}。`；其余 → “分化状态尚未形成一致方向”，`上涨占比{a:.2%}，中位数涨幅{中位涨幅:+.2%}。`
2. 分化：后 2 名行业里有任何一个 `return1d < 0` → “少数方向逆势承压”，否则 “普涨内部仍有相对强弱”；内容 `{行业1}、{行业2}分别为{r1:+.2%}、{r2:+.2%}。`
3. 量能：`c > 0` → “放量后的次日承接仍需验证”，否则 “缩量与炸板共同降温”；内容 `成交额环比{c:+.2%}，{触板}家触板中{未封}家未封住。`

**四个次日验证 `nextValidations`**
1. 广度：`a > 0.65` → “广度扩张能否延续”：`上涨占比继续高于50%，且MA20上方比例不显著低于今日{m:.1%}。`；`a < 0.35` → “广度与趋势存量是否继续背离”：`若上涨占比修复且MA20上方比例保持高位，分歧仍偏结构性；两者同步下滑则风险升级。`；其余 → “市场广度能否脱离分化区”：`上涨占比与MA20上方比例同向改善或恶化，才能确认状态迁移。`
2. `{最强方向}强势能否扩散`：`相对收益、上涨覆盖和成交占比至少两项继续改善。`
3. `{最弱方向}弱势能否收敛`：`相对收益不再恶化，且上涨覆盖回升。`
4. “封板生态能否稳定”：`封板率不低于今日{封板率:.1%}，多板梯队未明显塌缩。`

## 5. 次日假设与结算

每个交易日收盘后，按规则生成“下一交易日要验证的问题”；到期那天收盘后按规则自动结算。**只描述状态迁移，不是预测收益。**

### 5.1 生成（`engineVersion = daily-hypothesis-v1`）

记今天为 `D`，下一交易日为 `N`。`top` / `bottom` = 今天 16 个方向按 `return1d` 排序后的第一名 / 最后一名。ID 格式 `HYP-YYYYMMDD-<SLUG>`（日期为 `D`）。

| SLUG | 标题 | 范围 | 确认条件（全部满足） | 失效条件 |
|---|---|---|---|---|
| `MARKET-PERSISTENCE` | 广度、趋势存量与量能能否共同延续 | market | `advanceShare ≥ 0.50`；`aboveMa20Share ≥ max(0.60, 今日值 − 0.10)`；`turnoverCny ≥ 今日 × 0.90` | `advanceShare < 0.40`；或（`turnoverCny < 今日 × 0.85` 且 `aboveMa20Share < 今日值 − 0.08`） |
| `TOP-DIRECTION` | `{top}`居前能否转化为内部扩散延续 | direction | 该方向 `relativeVsAllA > 0`；`advanceShare ≥ max(0.55, 今日值 × 0.70)`；`amountShare ≥ 今日值 × 0.75`；`medianReturn1d ≥ 0` | `relativeVsAllA < 0` 且 `advanceShare < 0.45` |
| `WEAK-DIRECTION` | `{bottom}`相对弱势能否收敛 | direction | `relativeVsAllA ≥ −0.005`；`advanceShare ≥ 0.45`；`medianReturn1d ≥ 0` | `relativeVsAllA ≤ min(−0.01, 今日 relativeVsAllA)` 且 `advanceShare < 0.35` |
| `LIMIT-ECOLOGY` | 封板质量、晋级梯队与负反馈能否保持协调 | market | `sealRate ≥ max(0.75, 今日 − 0.08)`；`multiBoardCount ≥ max(5, round(今日 × 0.70))`；`limitDownCount ≤ max(3, 今日 + 2)` | `sealRate < 0.65`；或（`multiBoardCount < max(2, round(今日 × 0.50))` 且 `limitDownCount > 今日 + 3`） |
| `DIRECTION-SPREAD`（仅当 `spread ≥ 0.03`） | 方向高低剪刀差是收敛还是继续扩大 | direction | `N` 日 `spread ≤ 今日 spread × 0.75` 且弱方向 `advanceShare > 今日弱方向 advanceShare` | `N` 日 `spread ≥ 今日 spread` 且弱方向 `advanceShare ≤ 今日值` |

- `spread = top.relativeVsAllA − bottom.relativeVsAllA`（结算时用同两个方向在 `N` 日的值重新算）。
- 规则类型名沿用老账本（导入的老记录也用这些名字）：`MARKET-PERSISTENCE` → `MARKET_PERSISTENCE`，`TOP-DIRECTION` → `DIRECTION_PERSISTENCE`，`WEAK-DIRECTION` → `DIRECTION_REPAIR`，`LIMIT-ECOLOGY` → `LIMIT_ECOLOGY`，`DIRECTION-SPREAD` → `DIRECTION_SPREAD`。
- `hub market eod` 和 `backfill` 只在 `date ≥ config/market.yaml 的 hypotheses.startDate` 时生成假设（更早的日期以老账本为准，见 `06`）。这个门槛只作用于这两个命令；生成函数本身对任何日期都能用（M-2 就是用 2026-08-28 检验）。
- 每条假设还要有中文说明字段，模板照下面写（`{}` 用当日数值填充）：
  - `MARKET-PERSISTENCE`：确认 `上涨覆盖不低于50%，MA20上方比例不低于{阈值:.1%}，且成交额不低于当日的90%。`；失效 `上涨覆盖低于40%，或成交额收缩超过15%且MA20上方比例同步下降。`；风险 `强扩散后的自然均值回归可能造成单日回落，确认规则只描述次日延续，不外推中期趋势。`；反证 `生成日上涨覆盖{a:.1%}、MA20上方{m:.1%}，高基数提高了延续难度。`
  - `TOP-DIRECTION`：确认 `{top}继续取得正相对全A收益、上涨覆盖不低于{阈值:.1%}，成交占比不低于生成日的75%。`；失效 `{top}相对收益转负且上涨覆盖低于45%，或方向中位收益转负。`；风险 `同花顺方向成员是当前快照，不是点时历史；次日若成员发生变化，结算质量必须降级为证据不足。`；反证 `生成日单日收益{r:+.2%}、相对全A{rel:+.2%}，短期拥挤与分化风险上升。`
  - `WEAK-DIRECTION`：确认 `{bottom}相对全A落后幅度收窄至0.5个百分点以内，上涨覆盖回到45%以上，且方向中位收益不再为负。`；失效 `{bottom}继续取得负相对收益且上涨覆盖低于35%，弱势扩散到方向中位数。`；风险 `低位方向可能仅受风格轮换扰动；单日收敛不等于中期修复。`；反证 `生成日收益{r:+.2%}、相对全A{rel:+.2%}、上涨覆盖{adv:.1%}。`
  - `LIMIT-ECOLOGY`：确认 `封板率不低于{阈值:.1%}、多板梯队不少于{n}家、跌停不超过{k}家。`；失效 `封板率低于65%，或多板梯队缩减过半且跌停家数明显增加。`；风险 `不同交易板与ST状态涨跌幅制度不同，必须沿用逐股涨跌停价口径。`；反证 `生成日封板率{s:.1%}、多板{n}家、跌停{k}家；强基数可能快速回落。`
  - `DIRECTION-SPREAD`：确认 `最强与最弱方向的相对收益差由{spread:.1%}收敛至少25%，同时弱方向上涨覆盖改善。`；失效 `剪刀差不降反升，且弱方向上涨覆盖继续下降。`；风险 `剪刀差收敛可能来自强方向回落，也可能来自弱方向修复，必须分解两端贡献。`；反证 `生成日最强{top}与最弱{bottom}相对收益差为{spread:.1%}。`
- 说明文字沿用老系统，个别地方比规则多写了一句（比如 `TOP-DIRECTION` 失效说明里的“或方向中位收益转负”）；**判定一律只按上表的条件**。
- 假设记录保存规则类型、阈值和生成日基线值，结算时只用这些保存下来的数，不重新推导。

一条假设的结构（契约模型 `Hypothesis`；API 里每条一行，按 `id` 覆盖写入；同一 `id` 已经结算的保留原结果，只有仍是 `PENDING` 的才覆盖）：

```jsonc
{
  "id": "HYP-20260828-TOP-DIRECTION",
  "createdOn": "2026-08-28",
  "dueOn": "2026-08-31",
  "mode": "realtime",                 // realtime：当天收盘后生成；backfill：补跑时生成
  "engineVersion": "daily-hypothesis-v1",   // 可选；导入的老记录照搬 generation.engineVersion
  "title": "文化传媒居前能否转化为内部扩散延续",
  "scope": "direction",               // market | direction；导入的老记录还有 theme | sector | index
  "confirmation": "……", "invalidation": "……", "risk": "……", "counterEvidence": "……",
  "rule": {                           // 老账本最早的 11 条手写假设为 null
    "type": "DIRECTION_PERSISTENCE",
    "entity": "文化传媒",               // 方向类才有；剪刀差用 "entities": [强, 弱]
    "thresholds": { "relativeMin": 0.0, "advanceShareMin": 0.55, "amountShareMin": 0.0172, "advanceShareInvalid": 0.45 },
    "baseline": { "membershipAsOf": "2026-08-28", "return1d": 0.0066, "advanceShare": 0.6378, "amountShare": 0.0229 }
  },
  "result": "PENDING",                // PENDING | CONFIRMED | NOT_CONFIRMED | INCONCLUSIVE
  "settledOn": null,
  "actual": null,                     // 结算时的实际输入值
  "resultNote": "等待 2026-08-31 收盘结算。"
}
```

### 5.2 结算

- `N` 日的 `run` 完成后，对所有 `dueOn = N` 且结果还是 `PENDING` 的假设结算：满足确认条件 → `CONFIRMED`；否则满足失效条件 → `NOT_CONFIRMED`；两者都不满足 → `INCONCLUSIVE`（证据不足）。
- 方向类假设在 `N` 日找不到该方向 → `INCONCLUSIVE`，说明“到期快照缺少该方向”。
- `rule = null` 的老账本手写假设到期 → 一律 `INCONCLUSIVE`，说明“手写假设无可复算规则”。
- `N` 日需要的数据块缺失 → 保持 `PENDING`，等补跑；超过 3 个交易日仍缺 → `INCONCLUSIVE`，说明“数据缺失”。
- 结算时记下实际输入值 `actual` 和一句说明：`规则{类型}按{N}收盘结算为{结果}；实际：{字段=值, …}`（比例和收益写成 1 位小数的百分比，`spread` 写成“个百分点”、1 位小数，成交额写成“亿元”、1 位小数，家数写整数，日期原样；别把原始长小数直接写进说明）。

### 5.3 统计口径（修正）

- **Research Error 只算 `NOT_CONFIRMED`**。`INCONCLUSIVE` 单独统计为“证据不足”。老周报把两者合并，是错的。
- 验证中心页面显示：累计以及近 20 个交易日的确认 / 未确认 / 证据不足数量和占比，按规则类型分开统计。“近 20 个交易日”按结算日算；占比的分母是已结算的条数（不含 `PENDING`）；没有规则的老手写假设单独归为“手写（无规则）”一类。

## 6. 演化与周报

### 6.1 近五日演化 `MarketDay.evolution`

演化作为当天 `MarketDay` 的一块（所以历史上每一天都能看到“当时的”演化）。输入：当天的完整计算结果 + 前 4 个交易日的 `MarketDaySummary`（从 API 读）：
- 每天一行：日期、温度、情绪、`advanceShare`、`aboveMa20Share`、`turnoverCny`、涨停、跌停、最高板、封板率、`trendStrongShare`、前 3 方向、前 3 行业。
- `edgeChanges`（最近两天对比 4 项）：市场量能（成交额变化率，扩张/收缩）、上涨覆盖（差值，扩大/收窄）、涨停生态（涨停家数差，扩张/压缩）、前排高度（最高板差，抬升/压缩/持平）。
- `summary`：成交额中位数、温度区间、上涨覆盖区间、方向和行业在每日前 3 中出现的次数（各取前 6）。
- `transmission` 四段：量能与广度（成交额较前日变化、上涨覆盖、五日成交中位）→ 方向承接（当日第一方向及收益）→ 涨停聚类（涨停最多的行业、家数、最高板）→ 负反馈（跌停家数 / 晋级未完成家数）。
- `signals`：下一交易日“乐观与悲观信号并列”，4 项，每项有当前状态、确认条件、失效条件（老站这块逻辑写在前端，新系统移到 Python）：

| 项 | 当前状态 | 确认 | 失效 |
|---|---|---|---|
| 量能承接 | 今日成交额 ≥ 五日成交中位 → “乐观条件已满足”，否则 “仍待确认” | `成交维持或高于近五日中位 {五日中位，亿元}` | `放量冲高后快速回落，且低于五日中位` |
| 方向延续 | 当日第一方向的名称 | `{方向}继续居前且内部上涨覆盖不收窄` | `龙头断板、居前方向跌出前三且负反馈扩散` |
| 前排晋级 | 前日晋级率（百分比） | `晋级率回升、最高板不压缩，炸板率下降` | `晋级率继续下滑，最高板压缩且掉队增多` |
| 市场广度 | 上涨覆盖（百分比） | `上涨覆盖维持且中位数同步改善` | `指数上涨但中位数、上涨覆盖明显回落` |

- 最近 60 个交易日的趋势图（温度、情绪、上涨覆盖、MA20 上方、成交额、涨停、跌停、最高板）不存进文档：网站构建时直接读 `GET /v1/public/markets/days?limit=60` 的摘要来画。

### 6.2 周报 `WeeklyReport`

- 在本周最后一个交易日（下一交易日在下一周）生成，取最近 5 个交易日。
- 标题：上涨覆盖首尾变化 > 0 且 MA20 上方首尾变化 > 0 → “广度与趋势存量同步改善”；只有前者 > 0 → “广度改善但趋势存量未同步”；否则 → “广度回落，结构持续性接受检验”。
- 一句话：`五个交易日内，上涨覆盖变化{Δa:+.2%}、MA20上方比例变化{Δm:+.2%}、成交额首尾变化{Δturnover:+.2%}；结论只描述状态迁移。`
- 六节：
  1. **上周判断验证**：这 5 天内结算的假设数量，分确认 / 未确认 / 证据不足 / 到期未结算，并逐条列出（标题、结果、说明）。
  2. **真正改变结构的三件事**：市场广度（扩张/收窄）、趋势存量（改善/弱化）、市场量能（扩张/收缩），各附反证边界一句：`首尾变化不能代替日内路径，需同时查看五日区间。` / `MA20状态具有滞后性，不等于次日方向。` / `量能需与上涨覆盖、封板质量共同判断。`
  3. **持续、反复与转弱**：持续居前方向（5 天里进入前 3 至少 2 次，附次数）；反复方向（`relativeVsAllA` 正负号切换 ≥ 2 次，按切换次数排序，最多 8 个）；最新弱势方向（最后一天的后 3 名）。
  4. **Research Error**：只列未确认的假设（修正）；另列到期未结算的。
  5. **下周只验证三件事**：`{最后一天第一方向}能否连续保持相对收益与内部扩散`（确认：相对全A收益为正且上涨覆盖不收窄；失效：相对收益转负且内部中位同步转弱）；`广度改善能否获得量能与MA20趋势存量共同支持`（确认：上涨覆盖、成交与MA20上方比例至少两项改善；失效：指数维持但中位数和上涨覆盖同步回落）；`封板生态是否出现高位压缩与负反馈扩散`（确认：封板率、晋级梯队和跌停数量保持协调；失效：高度压缩、晋级率下降与跌停增加同时出现）。
  6. **数据说明**：使用了哪 5 天、缺了什么；结尾“研究辅助，不构成投资建议。”
- 输入：本周 5 个交易日的 `MarketDaySummary`（含 16 个方向各自的相对全 A 收益）+ 本周结算的假设。
- `WeeklyReport` 同时带一份 Markdown 版（字段 `markdown`），照上面的结构输出；网页和 Markdown 内容一致。

### 6.3 事件日历 `MarketEvent`

- 存在 API 的 `market_events` 表，在控制台维护（增、改、删），字段：`id` `startDate` `endDate` `title` `status`（`confirmed` 官方已确认 / `pending` 待官方确认）`sourceLabel` `sourceUrl` `watchItems[]` `aShareMappings[]` `confirmation` `invalidation`。
- 页面显示未来 30 天和过去 7 天的事件；`pending` 的必须显示“待官方确认”。
- 首批数据从老系统迁移（79 条，见 `06`）。
- 以后可做（不在本期）：每周一次用带联网搜索的 LLM，扫描 `config/market_event_sources.yaml` 里的官方来源，把候选事件以 `pending` 状态写进事件日历，让 Kevin 在控制台确认。
