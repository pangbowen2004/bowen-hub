# 10 AI 能力层（智能平面）

> 这一层回答：系统里哪些地方用 AI、怎么用、换更强的模型时怎么保证“真的变好了”。
> 核心思路：**AI 是可替换的零件，不是散落在代码里的 API 调用。** 每个用到 AI 的地方都是一个“能力”，有清单、有输入输出契约、有评测、有降级。

## 1. 四条原则

1. **确定性的事交给代码，判断和写作交给模型。** 采集、去重、打分、计算、校验、组版都是普通代码；模型只拿到整理好的“事实包”，负责挑选、归纳、写中文。事实包里的数字一律是人读的写法（`+1.23%`、`$35.1B`），不给模型 0–1 小数，也不让模型换算。
2. **输入输出都有契约。** 每个能力的输入和输出模型都定义在 `contracts/capabilities.tsp`，两种语言用同一份生成的类型；模型的输出不符合结构就当失败处理。
3. **写出来的东西要能核对。** 输出里的数字、引用、页码，由确定性的校验逐条检查（第 5 节），核对不上的删掉或整条降级。
4. **换模型靠评测说话。** 模型、提示词、档位的任何改动，都先跑评测（第 7 节），分数不降才合并。

## 2. 目录

```text
capabilities/                 每个能力一个清单文件
  news.edition_lede.yaml
  news.ticker_digest.yaml
  ...
prompts/                      提示词（Markdown）
evals/                        每个能力一个评测目录（第 7 节）
config/llm.yaml               模型登记表：档位 → 模型、单价、网关
contracts/capabilities.tsp    每个能力的输入 / 输出模型
py/packages/hub-ai/           Python 运行时（Pydantic AI + pydantic-evals）
packages/ai/                  TypeScript 运行时（AI SDK 6）
```

`hub-ai` 依赖 `hub-contracts` 和 `hub-core`（用 `hub-core` 的 API 客户端写调用记录和评测结果、读反馈）；领域包再依赖 `hub-ai`。

## 3. 能力清单（`capabilities/<id>.yaml`）

```yaml
id: news.ticker_digest
version: 1                 # 提示词、输入输出或校验变了就 +1；产出里的 generatedBy 会带上它
summary: 为一只自选股写“发生了什么 / 为什么重要”
owner: newsroom            # 所属领域
runtime: python            # python | typescript（在哪一端运行）
tier: balanced             # fast | balanced | frontier（第 4 节）
autonomy: L2               # L0–L3（第 6 节）
prompt: prompts/news_ticker_digest.md
io:
  input: TickerDigestInput     # contracts/capabilities.tsp 里的模型名
  output: TickerDigestOutput
limits:
  maxInputTokens: 20000
  maxOutputTokens: 800
  timeoutSec: 60
checks:                    # 确定性后置校验（第 5 节），按顺序执行
  - numbers_in_sources
  - source_ids_exist
  - no_advice
fallback: headlines        # 失败时调用方怎么降级（具体做法写在产品文档里）
params: {}                 # 能力自己的参数（如 papers.author 的 repairRounds、reviewRounds）
evals:
  dataset: evals/news.ticker_digest/
  schedule: weekly         # weekly（默认，参加每周全量评测）| on-change（只在改动时跑）
  thresholds:              # 评测阈值（第 7 节），低于任何一项就不合格
    schema_valid: 1.0
    numbers_in_sources: 1.0
    judge_faithful: 0.9
```

本期的能力：

| 能力 | 运行端 | 档位 | 自治 | 用在哪 |
|---|---|---|---|---|
| `news.edition_lede` | Python | frontier | L2 | 早报导语、盘前“今晚三件事”、周报“本周主线”（`02` 第 6 节） |
| `news.ticker_digest` | Python | balanced | L2 | 自选股动态、周记 |
| `news.us_rank` | Python | balanced | L2 | 美股要闻 6–8 条 |
| `news.earnings_card` | Python | balanced | L2 | 财报卡片 |
| `news.filing_digest` | Python | fast | L2 | 8-K 要点 |
| `news.classify` | Python | fast | L2 | 国际与科技栏目：分主题 |
| `news.curate` | Python | balanced | L2 | 国际与科技栏目：Top 5 + 综述 |
| `news.brief` | Python | fast | L2 | 国际与科技栏目：中文摘要（2–3 句） |
| `papers.author` | Python | frontier | L1 | 新论文的导读草稿（`04` 第 5 节） |
| `papers.review` | Python | frontier | L1 | 草稿审核 |
| `papers.qa` | TypeScript | balanced | L2 | 控制台和 MCP 里“问这篇论文” |

## 4. 模型档位（`config/llm.yaml`）

代码和清单里只写档位，不写具体模型。**档位 → 模型只在 `config/llm.yaml` 定义一次**：

| 档位 | 用途 | 起步配置（2026-09-29） |
|---|---|---|
| `fast` | 分类、短摘要、公告要点：量大、简单 | `openai/gpt-6-luna`，推理强度 none |
| `balanced` | 个股动态、要闻排序、财报卡片、论文问答 | `openai/gpt-6-luna`，推理强度 medium |
| `frontier` | 导语、论文导读与审核：要综合判断、长文写作 | `openai/gpt-6-sol`，推理强度 high |

- 起步配置偏省钱。哪一档不够好，由评测决定是否换成更强的模型（比如 `balanced` 换成 `gpt-6-sol`、`frontier` 换成 `gpt-6-astra`）。
- 所有调用都走 Cloudflare AI Gateway 的统一接口（OpenAI 兼容，模型名写成 `供应商/模型`）：`https://gateway.ai.cloudflare.com/v1/{CLOUDFLARE_ACCOUNT_ID}/{AI_GATEWAY_ID}/compat`，请求头带 `OPENAI_API_KEY`。网关统一记录日志、用量和费用；以后接别的供应商只改模型名。
- 单价表也在 `config/llm.yaml`，用来算每次运行的费用（写进 `ai_calls`，在控制台“运维”页和邮件页脚显示）。
- 月度预算 `monthlyBudgetUsd`：超过时只提醒（失败通知邮件 + 控制台红字），不自动降级。由每晚数据导出（`hub export`）结束时检查本月 AI 费用，超了就发这封提醒并在 `runs` 表记一条 `budget-alert`，同一个月只发一次（`09` 第 5 节）。

## 5. 运行时

两端做的事完全一样，只是语言不同：

```text
run_capability(id, input)
  1. 读清单 → 按档位从 llm.yaml 取模型和参数
  2. 用输入渲染提示词（第 5.1 节）
  3. 调模型，要求按输出模型的 JSON Schema 返回（结构化输出）
  4. 用生成的校验器检查结构；不合格 → 带着错误信息重试 1 次
  5. 按清单顺序跑确定性校验（第 5.2 节）
  6. 给输出盖上出处：generatedBy = { capability, version, model, at }
  7. 回调记录：能力、版本、模型、token、费用、耗时、成败、所属运行
  8. 返回 Result：成功（带输出和校验报告）或失败（带原因）；由调用方决定是否降级
```

- **Python**（`hub-ai`）：Pydantic AI 的 Agent，模型用 OpenAI 兼容接口指向网关；结构化输出优先用原生 JSON Schema 模式，供应商不支持时用工具调用模式（Pydantic AI 的默认做法）。
- **TypeScript**（`packages/ai`）：AI SDK 6，`generateObject` / `streamText`；清单、提示词和 `llm.yaml` 在构建时编进一个生成的注册表模块（Worker 里不读文件）。本期只有 `papers.qa` 在这一端运行，流式返回。论文 HTTP 入口在 CPU 实测超预算后使用领域原生 SSE 传输 Adapter，清单选择、预算、校验与记账仍交给同一 Runtime；普通结构生成和内部非 HTTP 流路径保留 AI SDK。
- 超时、重试（最多 2 次，默认 1 s、2 s 退避；Python 网关适配器遇 HTTP 429 提供有效 Retry-After 秒数时等待至少该间隔，单次上限 60 s）、token 上限都按清单的 `limits`。
- 测试时用假的模型（Pydantic AI 的 `TestModel` / `FunctionModel`，AI SDK 的 mock 模型），不联网。
- **流式能力**（`papers.qa`）：边生成边返回；校验在流结束后进行，只做标注、不删改已经发出的内容（例如越界的页码不进入最终的 `pages`，界面上标出）。如果逐块解析会让 Worker 超出 CPU 限制，就直接转发网关的流，结束后再从全文里提取页码。
- **校验注册**：通用校验（第 5.2 节前六个）由运行时提供；领域校验由领域包注册（`paper_draft` 由 `hub-papers` 注册），运行时按清单里的名字调用。
- **契约里的标注**：输出字段的字数上限、“原文片段”字段、输入里的图片字段，在 `contracts/capabilities.tsp` 里用自定义扩展 `x-max-chars`、`x-source-quote`、`x-image` 标注（不用 `maxLength`）；生成的校验器不强制这些标注，由运行时读取（`length_within`、`quotes_in_sources`、图片附件）。同一字段的上限随 `mode` 变化时（如 `whatHappened` 日报 80 字、周记 60 字）标较宽的一档，较严的一档靠提示词约束。

### 5.1 提示词格式

```markdown
# news_ticker_digest —— 一句话说明（给人看）

> 任何说明文字（给人看，运行时忽略）

## system
……

## user
……{{ symbol }}……{{ articles }}……
```

- 运行时只取 `## system` 和 `## user` 两节；`<!-- -->` 注释会被去掉。
- 占位符只有一种写法：`{{ 字段名 }}`，字段名就是输入模型的顶层字段（camelCase）。字符串原样放入；对象和数组序列化成 JSON（两空格缩进、保持输入的键顺序、不转义中文；事实包里的数字本来就是人读的字符串，不放浮点数）；值为 null、空字符串或空数组时写成“（无）”。**不支持条件和循环**：需要分情况的，用输入里的字段说明（比如 `mode: premarket`），由提示词自己写清楚每种情况怎么做。
- 图片：输入模型里标为图片的字段（如 `papers.review` 的 `pageImages`）由运行时作为图片附件随 user 消息发送，占位符处只写页码。
- 提示词里可以写“返回的 JSON 结构”，但真正约束输出的是契约里的输出模型。

### 5.2 确定性校验（名字写在清单的 `checks` 里）

| 校验 | 规则 | 不通过时 |
|---|---|---|
| `numbers_in_sources` | 只核对输出文字里的“量”：带单位的数（`%`、`$`、倍、bp、万 / 亿 / 万亿、thousand / million / billion 等）和三位以上的裸数字。规范化后（去千分位、`$`、`%` 和正负号，`1.2 billion` ↔ `1.2B` ↔ `12 亿`）必须出现在输入里（原文或事实包）。日期、时刻、年份、季度、表格名（8-K、Form 4）、Item 编号（5.02）、指数名（标普500）里的数字跳过；月份名与数字（October ↔ 10 月）、`Q3` 与“第三季度”先归一再比 | 删掉含该数字的句子；整条都没了就降级 |
| `quotes_in_sources` | 输出模型里标为“原文片段”的字段（如财报卡片的 `quote`、审核的 `sourceExcerpt`）必须是输入原文的子串；比较时忽略空白差异，并去掉页文本每行前面的行号前缀 `L{行号}: `（`04` 第 5.1 节） | 删掉该项 |
| `source_ids_exist` | 引用的 `sourceIds` / `id` 都在输入里 | 删掉不存在的引用；给了引用但全部无效才降级（本来就没给引用不算失败） |
| `no_advice` | 不出现买卖建议、目标价、仓位（词表在 `config/newsroom.yaml` 的 `adviceWords`） | 删掉该句 |
| `length_within` | 各字段字数不超过输出模型里标注的上限 | 截到最后一个完整句 |
| `pages_in_range` | 引用的页码在 1 到总页数之间 | 删掉越界页码 |
| `paper_draft` | 论文草稿的全部格式与证据检查（`04` 第 5.2 节；由 `hub-papers` 注册） | 进入修订循环 |

校验报告随结果返回；删掉了什么都记在运行记录里，方便以后改提示词。

## 6. 自治等级：让系统随模型变强而变强

| 等级 | 含义 | 本期谁在这一级 |
|---|---|---|
| **L0 影子** | 照常运行、记录、评测，但结果**不进入任何产出** | 试运行新能力或新模型时 |
| **L1 草稿** | 结果进草稿，Kevin 确认后才生效 | `papers.author`、`papers.review` |
| **L2 自动** | 结果通过确定性校验后直接进入产出；不通过就降级 | 新闻各能力、`papers.qa` |
| **L3 自主** | 能力在预算内**自己决定步骤**：可以调用只读工具（如 MCP 的 `news_search`、查 SEC 公告），多步完成任务；结果同样要过校验 | 本期没有 |

**模型变强时，系统有四个“旋钮”可以拧，全都不用改业务代码：**

1. **换档位映射**：`config/llm.yaml` 里把某一档指向更强的模型。
2. **升档**：把某个能力的 `tier` 从 `balanced` 改成 `frontier`。
3. **放宽上下文**：比如论文问答已经把整篇论文放进上下文（GPT-6 系列上下文约 105 万 token，见 OpenAI 模型页，2026-09-29 核对）；以后更长的材料同样直接放进去，不用做检索。
4. **升自治等级**：L0 → L2（影子运行达标后转正）；L2 → L3（例如以后的“新闻调查员”：自己去查公告和历史新闻，把一条消息讲透）。

升级的规矩：改一个旋钮 = 一个 PR；PR 里附上 `hub evals compare` 的对比表（第 7.3 节）；分数不低于现状、费用在预算内，Kevin 点头后合并。

## 7. 评测（`evals/`）

### 7.1 评测集

```text
evals/
├── README.md
└── news.ticker_digest/
    ├── cases.yaml               # 评测用例
    ├── judge_faithful.md        # judge 类评分器的评分标准，每个 judge 一个文件
    └── judge_specific.md
```

`cases.yaml` 里每条用例：`id`、`input`（能力的输入，JSON）、`expect`（可选：必须包含 / 不能包含的内容、参考答案、正确标签）、`tags`（来源：`fixture` 录制数据 / `feedback` Kevin 的反馈 / `edge` 手写边界情况）。

用例的三个来源：
1. **录制的真实输入**：开发时从 `fixtures/` 和真实运行里截取。
2. **Kevin 的反馈**：控制台里标了“没用”或“有错”的条目，`hub evals harvest` 把它们转成用例草稿（`tags: [feedback]`），人工补上 `expect` 后入库。`news.ticker_digest`、`news.us_rank` 的 `input` 由已存的 `Edition`（条目带来源 id）和 `articles` 表重建；其他能力只生成“输出 + 来源链接”的草稿，`input` 由人补上。
3. **手写的边界情况**：没有消息的股票、同一事件多家报道、财报里的调整后与 GAAP 数字并存、论文里的负结果等。

每个能力起步至少 10 条用例；`news.us_rank`、`news.ticker_digest`、`papers.qa` 至少 20 条。

### 7.2 评分器（`hub-ai` 内置）

评审输出预算独立使用 `config/llm.yaml` 的 `defaults.judgeMaxOutputTokens: 4096`，包含推理 token 与评分结果，仍使用 `balanced` 档并计入同次评测费用和月度预算。正文能力的 `limits.maxOutputTokens` 不变。真实新闻筛选验收证实原硬编码 512 在推理阶段耗尽、尚未产生评分结果；独立预算也避免把短正文（如 300 token 的公告摘要）的上限错误套给评审。超限明确失败，不降低质量阈值或改用离线分数。

| 评分器 | 打分方式 |
|---|---|
| `schema_valid` | 输出结构合格的比例 |
| 第 5.2 节的每个校验（`numbers_in_sources`、`quotes_in_sources`、`source_ids_exist`、`no_advice`、`length_within`、`pages_in_range`、`paper_draft`） | 同名校验，统计无需删改（一次通过）的比例 |
| `labels_match` | 分类类能力：与 `expect` 里的标签一致的比例 |
| `must_include` / `must_exclude` | 是否包含 / 不包含 `expect` 里列出的要点 |
| `judge_*` | 用同名的 `judge_*.md` 评分标准请模型打 0–1 分（评审模型用 `balanced` 档；只用在少数需要主观判断的维度，如“忠实于原文”“为什么重要是否具体”） |

### 7.3 什么时候跑

| 时机 | 范围 | 命令 |
|---|---|---|
| PR 改动了 `capabilities/`、`prompts/`、`evals/`、`config/llm.yaml` | 只跑受影响的能力 | `hub evals run --changed` |
| 每周日 03:00（新加坡） | 除清单里标了 `evals.schedule: on-change` 的能力以外的全部能力（发现供应商那边的变化）；`papers.author`、`papers.review` 单次评测较贵，只在改动时跑 | `evals-weekly.yml` |
| 考虑换模型 | 指定能力或全部，现配置 vs 候选模型 | `hub evals compare --candidate openai/gpt-6-astra [--capability <id>]` |

评测统一由 Python 运行时执行（清单里的 `runtime` 只决定产品里在哪一端运行；两端的提示词渲染用同一组测试向量保证一致）。每周评测的结果写进 API 的 `eval_results`（PR 里的评测只出报告、不写 API），控制台“运维 → 评测”页显示每个能力的分数走势、费用和耗时。`compare` 另外输出一张 Markdown 对比表，贴进 PR。`--capability` 可以写通配，如 `'news.*'`。

## 8. 新增一个能力的步骤

```bash
mise run new:capability news.foo     # 生成清单、提示词、评测目录、契约里的输入输出模型骨架
```

1. 在 `contracts/capabilities.tsp` 写好输入输出模型 → `mise run gen`。
2. 写提示词和至少 10 条评测用例。
3. 以 L0 接入调用方（只记录，不进产出），跑评测直到达标。
4. 改成 L2（或 L1），PR 附评测结果。

## 9. 本期不做

- 向量库和检索增强：本期的材料（一期新闻、一篇论文）都能直接放进上下文。
- 让模型自己调用工具的 L3 能力。
- 微调、本地模型。
